# 阵码与坐标契约

## 文件与阵型容器

统一写 UTF-8，优先无 BOM。规范文件如下，多阵用 `/` 分隔，换行只用于阅读：

```text
baseline&<纯阵码>/
candidate-001&<纯阵码>/
candidate-002&<纯阵码>
```

尖括号是占位符，不能传给模拟器。阵名不含 `/`、`&`、`#` 或换行。名称与编码分开保存，代码哈希只对纯阵码计算。实际示例见 [candidate.txt](examples/candidate.txt)。

`Setting.parseFortsRaw` 按 `/` 切分，再取最后一个 `&` 后的部分，并删除非 ASCII 字母数字。两条 `name&code` 只用换行连接，会被误读成一条。旧阵集常在 `&` 后夹作者署名：导入时保留原文，再显式清洗、记录对应关系、核对条数与每条编码，不把“解析没报错”当成完整导入。

本套 `kit_lab.py` 故意严格拒绝非规范字符、缺失分隔符和 `#HP`，不会自动吞掉异常条目。它不会自动去重：本工作区标准200必须保留冻结的全部条目和顺序；另建评测池时才自行确定去重与权重规则。

## 编码基数与单元

Java 密码表常量是：

```text
0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ
```

**这串长度是 62，但数值计算的基数为 61。** 规范坐标编码的数字取下标 0–60，即到大写 `Y`；不要使用通用 base62。`Z` 是下标 61，虽然某些解码路径会接收，但不属于本工作流生成的规范坐标数字。

纯阵码长度至少 6，且是 6 的倍数。第 0 个六字符单元是核心，之后每个单元是一个非核心单位：

```text
type + d4 d3 d2 d1 d0
N = d4*61^4 + d3*61^3 + d2*61^2 + d1*61 + d0
r = N // 1000000
raw_x = (N // 1000) % 1000
raw_y = N % 1000
```

普通单位类型字符 = 密码表下标，合法非核心 ID 为 1–60。核心首字符 `0`、`1`、`2` 对应工作台 ID `0`、`61`、`62`。核心只能放在第一槽；不能把 BOSS 核心的工作台 ID 当成普通单位类型字符直接追加。

## 坐标必须具名

工作流统一用 **工作台坐标** `x, y, r` 描述编辑。不要混用下表各列：

| 对象 | 编码中的 raw 坐标 | 工作台坐标 | 引擎编译数据 |
|---|---|---|---|
| 核心 | `raw_x, raw_y` | `x=raw_x-52, y=raw_y-58` | `coreX=raw_x-190, coreY=raw_y-400` |
| 兵玉/壁/加速器 | `raw_x, raw_y` | `x=raw_x-16, y=raw_y-20` | `CompiledFort.x/y` 保留 raw 坐标 |

普通单位在 1P 的初始游戏坐标是 `raw_x+50, raw_y+132`，即工作台 `x+66, y+152`。2P 的初始游戏坐标为 `1870-raw_x, raw_y+132`，方向为 `180-r` 后归一化。两侧的核心还会结合各自车体位置，不要用普通单位公式处理核心。

Kit 工作台会把核心 `x/y` 裁到 `0..276`，普通单位 `x` 裁到 `0..348`、`y` 裁到 `0..349`，角度归一到 `0..359`。这些是 **Kit 工作台边界**，并不是某个比赛的完整合法性规则。AI 生成候选应事先满足边界，并拒绝越界而不是让 GUI 静默裁剪，否则比较的阵码会变。

核心通常保留原 `r`；无明确理由时生成普通核心用 `r=0`。编码的核心位置同时影响 Rust 默认种子，因此移动核心可能同时改变几何与随机序列。

### 横坐标也是攻击时序参数

横移同时改变几何与初始化计数，核心位置还影响默认种子；不能当纯几何变化。公式、有效计数与触发周期维护在[基础机制](08-formation-fundamentals.md#1-坐标改变的不只是位置)及[弹幕时序](13-volley-timing.md)，具体兵种查单位百科。固定配对只来自本轮rules或用户要求。

## 正向编码

对工作台坐标重新编码：

```python
ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"

def encode_unit(unit_id, x, y, r, *, core=False):
    assert 0 <= r < 360
    assert 0 <= x <= (276 if core else 348)
    assert 0 <= y <= (276 if core else 349)
    if core:
        type_char = {0: "0", 61: "1", 62: "2"}[unit_id]
        raw_x, raw_y = x + 52, y + 58
    else:
        assert 1 <= unit_id <= 60
        type_char = ALPHABET[unit_id]
        raw_x, raw_y = x + 16, y + 20
    number = r * 1_000_000 + raw_x * 1000 + raw_y
    digits = ["0"] * 5
    for index in range(4, -1, -1):
        number, digit = divmod(number, 61)
        digits[index] = ALPHABET[digit]
    assert number == 0
    return type_char + "".join(digits)
```

以上 Python 代码须在 `conda activate opencode` 后执行。生成后调用 `audit`，核对 `roundtripCodeEqual=true`、成本、单位数及全部坐标，并检查 `encodedHasHpSuffix`。普通核心满血码通常还有 `roundtripEqual=true`。未修改槽位应保持原六字符块不变。

## 顺序与槽位

单位序列是战术参数。引擎按创建顺序更新实体，首个目标单位、治疗先后、突击壁与兵玉的先后关系等都可能受影响。不能为“格式整齐”按类型或坐标排序。

| 索引 | 核心 | 第一个非核心单位 |
|---|---:|---:|
| `Formation.units` / 文档 `slot` | 0 | 1 |
| `CompiledFort.type` / 贡献分析 `UnitRef.index` | 无 | 0 |

删除贡献分析返回的索引 `i`，对应原码块 `[6*(i+1), 6*(i+2))`。改名可以不改哈希；调序、移位、旋转都必须生成新的代码哈希。

## 预算与单位属性

使用 [单位数据](data/unit-catalog.json) 的 `cost` 对全部槽位求和，包括非普通核心。红加速器 ID 29 每个 +1 加速等级，蓝加速器 ID 30 每个 +2。

工作台只在总价超过 1500 时标红，没有自动阻止对战。模拟器能跑不代表符合赛制。另行检查禁用单位、科技限制、单位数量、重叠或特殊码限制等用户指定规则。`tech` 是原表字段，未明确规则时不要擅自累加成预算。

`CD`、`AT`、`shoot` 等原始字段用于分析攻击周期；`dmgRaw` 中部分数值带编码含义，不能直接拿它比较所有兵种的实际伤害或 DPS。战术要由完整对局检验。

## 血量后缀与残局

工作台 `Formation` 支持 `#` 后的 HP 编码。每 3 个槽位的 HP 打包为 `hp0*57600 + hp1*240 + hp2`，再编码成 4 位 base61，尾组使用 239 填充。

**普通对战的 `Setting.parseFortsRaw` 会剥离 `#HP`，`CompiledFort` 不携带初始 HP；独立 Rust 的编译数据也没有这个字段。** 不允许把残局码送入这些入口后仍宣称测试的是残局。旧 Rust `parse_forts` 甚至不会像新 Java 那样先剥离 HP；不要依赖其文本清洗来处理残局。

本任务的默认优化对象为满血普通阵。若要做残局，必须重新确认真实支持残局初始状态的运行环境和输入接口，另建实验规范。

**1.9.1 的 BOSS 工作台解码细节**：`Unit.decodeAsCore` 先按首字符下标构造 Unit，再把 ID 改成 61/62，没有同步重新初始化 HP。实测标准200中的 BOSS 阵“前中激光要塞(带突) 圣耀赤轮”会被工作台对象读成核心 HP=10，并在回编码时新增 `#HP`。其纯阵码部分回编码仍一致。评测标准200时直接使用冻结的原纯码，不把工作台回编码输出批量写回基准；也不要把这个 HP 字段当成引擎实际初始核心血量。
