# 造阵研究与执行流程

本页维护从原阵研究到交付的执行顺序。评分、阵池角色和规模统一查[阵集政策](10-benchmark-usage.md)，设计方法查[搜索设计](04-search-workflow.md)与[搜索经验](11-search-lessons.md)，记录格式查[实验契约](05-experiment-contract.md)。当前工具链为`formation_workflow generate/accept → gravity.py evaluate → verify_pool.py`；不存在其他生成包装子命令。

## 1 明确输入与允许改动

新任务保留用户名称、原纯码与SHA256，续跑先读STATE和rules，核对明确父阵、剩余预算、停止状态与已完成证据。冻结预算、核心、禁限、单位顺序、固定字段、配对、侧位、帧上限、种子政策、后端和超时；用户硬约束与阶段选择分别记录。工具历史默认值不代替本任务授权。

每次搜索、生成候选前读[基础机制](08-formation-fundamentals.md)，按实际解码ID读[单位百科](knowledge/units/README.md)中共享机制、本阵所有单位与核心；理解构造、支撑、攻击、受击/恢复/死亡与生成物，墙和加速器也覆盖。相同任务与版本可复用阅读，新增兵种/职责补读；仅缺项、矛盾、版本变化或新问题超出条目时追源码并补回知识。火线横移另读[时序](13-volley-timing.md)。

用`catalog/formation`辅助理解，但目录HP、工作台稳定化坐标和实际构造状态分别解释。当前派生源码与发行包DLL存在[HP规则差异](unit-hp-rules.md)，诊断前确认后端，不能用新源码重放自动代替旧DLL证据。

## 1.1 开搜前先充分研究原阵

原阵指用户本次提供的原码或STATE明确指定为起点的父阵。先回答如何运转、靠什么赢、为何失守，再生成搜索候选。

1. **结构与单位。** 解码后逐槽说明火力、防护/消弹、支撑、回复、加速、突击职责及依赖。检查预算、核心位置、顺序、初始加速、时序和静态支撑，记录知识版本与待验机制，不从兵种数量猜战术。
2. **三池完整基线。** 在同一冻结身份下取得200、2000、10433，逐池verify，保存W/L/D/U/E、固定N得分率及证据哈希；先核验复用同身份历史和重合对局，只补缺局。三池完整、E=0并核验通过前不开新候选搜索；阵池来源缺项另行标明，不能靠条数替代身份。
3. **重点研究200。** 关联逐对手结果与元数据，按相关兵种/组合、加速、核心类型/位置和攻防结构分群，列定义、N、W/L/D/U/E与得分率，注明重叠、小样本。用工作台检查、画像、核心热图或等义离线聚合定位优势/弱点，2000/10433用于核对更广相性，不能只存总分。
4. **解释代表胜败局。** 从主要优势群与弱点群选有问题的胜局、败局，必要时补D/U、临界局和反例。先读基础结果、帧数、可用HP与存活信息，再按问题复用或补少量基础/详细对战：检查实际出手/命中、消弹、关键单位、核心受创、支撑破坏、回复和突击落点。记录对手索引、输入、后端/HP规则及结果一致性；不同后端不一致时先诊断，不能确认原评测因果。不强制全量详细模式或删除贡献。
5. **落盘后开搜。** BASELINE或等价报告包含结构/单位阅读、三池核验、200分群、代表对局、获胜手段/失败路径、已知限制与首批“观察→机制假设→改动轴→预期改善群→副作用/失败判据”。STATE链接权威报告，分清事实、源码机制与待验解释，内容齐全后才标研究完成。

同任务同配置的三池和研究可复用，不因内部换父阵或开新批机械重跑；当前父阵已有数据继续分析，新增职责补读。换起始阵或证据身份变化时补齐对应基线；续跑只补缺项，不覆盖历史或恢复停止任务。

**来源原码与稳定态分别记账。** 原码先做规则/重力审计。未改动来源原码若不稳定，可仅对该冻结原码直接调用`evaluate_pool.py`完成只读三池诊断，保存失败审计并标“不具备新候选晋级资格”。该边界不适用于任何新增、修改或apply后的候选。稳定态是新纯码，须通过规则/重力审核、重新评测，不继承原码成绩，也不例行重复建立三池基线。

## 2 生成、稳定化与规则验收

前期以机制理解和有对照小批为主，有实测提升后扩大联合与密集搜索。用[生成器](generator.md)写短JSON计划，显式base/rules，程序负责组合、拒绝原因和保序去重；不逐阵手写脚本或反复粘贴阵码。`coordinate-micro-v1`用于组成和顺序固定的坐标/角度；`structural-fixed-speed-v1`用于普通核心结构、id轴和template，实际预算与初始等级逐阵重算。

生成输出是内部草稿。已经稳定时可直接先审后评；需apply时输出稳定态，再以相同rules做accept，核对固定字段、配对、预算、禁限、顺序与dropControl，保留全部源阵/别名映射。重力不通过不得开始新候选评测或交付；详细模型与侧位限制见[重力审核](gravity-audit.md)。

下面是路径示例，先准备本轮计划和规则；不含实际父阵的占位计划不能直接运行：

```powershell
conda activate opencode
python tools/ai/formation_workflow.py generate --plan experiments/next/plan.json --out experiments/next/generated
python tools/ai/gravity.py apply --input experiments/next/generated/candidates.json --out experiments/next/applied --timeout 300
python tools/ai/formation_workflow.py accept --source experiments/next/generated/candidates.json --applied experiments/next/applied --rules experiments/next/rules.json --exclude experiments/next/prior-candidates.json --out experiments/next/stable-candidates.json
```

首次没有历史候选时省略`--exclude`，跨批可重复指定。直接调用`formation_rules.check`时只有返回`None`才通过，错误字符串也是失败，不只检查异常。

## 评测与逐池核验

先按[环境准备](03-tool-runbook.md#环境准备)激活opencode。以下命令按顺序使用同一缓存，各阶段候选名单先冻结，输出目录独立；原阵只读诊断例外仍遵循上节身份边界。

```powershell
conda activate opencode
python tools/ai/gravity.py evaluate --candidates experiments/next/stable-candidates.json --audit-out experiments/next/preflight --timeout 300 --evaluation-timeout 3600 -- --opponents benchmarks/standard200/opponents.txt --side 1 --store experiments/next/cache/store.sqlite --out experiments/next/training --threads 24 --batch-size 64 --timeout 600 --time-limit 3400
python tools/ai/verify_pool.py --run experiments/next/training --candidates experiments/next/stable-candidates.json --opponents benchmarks/standard200/opponents.txt
```

验证2000和决赛10433沿用这组命令，分别替换冻结候选、opponents、audit-out和out，并按实际工作量调整超时。单批最多64阵、通常不超过12800局；2000通常`--batch-size 4`，10433通常`--batch-size 1`。三池各自verify后汇总名单、哈希和完成状态，没有自动双池/三池包装run或`--final-test`参数。阵池使用[已确认的固定版本](10-benchmark-usage.md#阵集角色与身份)，核对文件哈希后直接评测。

重合对局只在纯码、对手、物理侧位、引擎/适配器指纹、帧上限与种子政策一致，且原始文件哈希核验后复用。同分不同码不合并；评分政策变化可重聚合，不重复模拟。不同包装器有不同指纹，不能直接混库。

原始结果、物理侧位与反向索引见[数据契约](data-contract.md)。需要2P时使用`--side 2`，双方完整同N后按[评分政策](10-benchmark-usage.md#评分与晋级)分别报告与取均分。高1P入围后补2P属于有范围初筛，可能漏掉1P稍低而双侧更强的版本。

## 后台评测与续跑

<a id="21-后台评测与研究"></a>

默认非阻塞后台运行，保存完整命令、PID/会话ID、日志、输出、冻结输入及真实进程超时。使用可返回会话的执行方式，或`Start-Process -WindowStyle Hidden`，标准输出/错误分别重定向。确认启动后继续服务当前造阵问题的独立研究：聚合已核验对局、查机制、选择少量明确详细对照或准备不依赖在跑结果的计划；不靠频繁轮询等待。

评测器`--time-limit`是批间期限，单批`--timeout`与重力外层`--evaluation-timeout`另设；工具等待输出的时长不是进程超时。超时后先独立查进程、日志和完整结果，再处理。进度通常只读`progress.json/summary.json`；存在`gate.json`时核对其来源，最终以独立verify为准。原始chunk已落盘而汇总尚未刷新时，`completedCandidates=0`不表示没有对战。

正在评测的输入、规则和引擎不变。只读完整发布且核验的证据；新诊断独立输出与SQLite父目录、少量线程，避免共写库或raw路径、挤占主评测。顺序运行可复用同库；并行库汇合元数据时保留raw路径与SHA256。

停止时在对应评测out放STOP，于批次边界保存，并处理等待触发的驱动。恢复须有用户续跑指示，使用同一冻结输入和命令，不能改旧manifest扩池或换候选。用户中途提问及时回应；在跑不写已完成。

整批未完而指定纯码已有完整证据时，可另建明确名单的独立输出/缓存核验作分支父阵。零新增快照可在新输出预置STOP，加载缓存后要求`status=complete`、`newGames=0`且verify通过；不调用不存在的`--cache-only`。原批声明候选仍须完成，快照不重复计入唯一阵数。

## 2.2 搜索中持续研究候选，再决定下一步

每个有对照批次或方向完整发布并核验后，先研究再冻结依赖本批反馈的计划；不要求逐候选或逐底层chunk写长报告。独立在跑批次保持原冻结输入。

1. **对齐真实父阵。** 保存父阵/候选纯码、精确slot/字段、阵池、侧位与配置；原阵/当前推荐对比另列。逐对手`delta_i=s_candidate_i-s_parent_i`，s为胜1、D/U半分、负0，列改善/退步数、增加/损失/净计分与完整变化索引。父阵不同不能把全部分差归于一字段。
2. **解释受益和受损对象。** 按相关兵种/组合、加速、核心类型/位置和攻防结构列组定义、N、前后成绩及净计分/百分点。组可重叠，不相加，各池分开；持平也查改善与退步的抵消，预期群未改善须保留失败预测。
3. **比较有信息的竞争者。** 保留高分、温和变化、不同区域、持平或略低分但有独特收益的版本，必要时加入反预测方案。有效模块保留同父阵单项/联合对照，已有2000反馈参与选择，不只沿训练冠军扩圈。
4. **核验关键解释。** 先写预测，从改善/退步各选少量有问题的共同对手，比较父阵/候选基础信息，复用或补详细对局；无某类变化如实标无。确认输入、后端/HP规则、胜负、HP与结束帧一致，再查实际出手/命中、消弹、支撑/火力存活、核心受创/回复和落点的相关窗口与来源链。不一致先排错，不用全量遥测代替具体问题。
5. **形成下一步取舍。** 将解释标支持/否定/不确定，说明继续分支、换父阵、补反事实、小联合或暂停的依据，写目标群、副作用与失败判据。未验证机制可作小批问题，不能当确认规律据此密集扩搜。及时写LEARNING与STATE，不等结束后倒填理由。

分析含义与共同条件统一见[分析使用](knowledge/analysis-usage.md)，联合交互、计分饱和和收敛边界见[搜索经验](11-search-lessons.md)。已有结果和元数据先离线重聚合，调用matchup/strength前确认是否新增模拟。基础诊断先摘要和指定槽位，再按需要[详细重放](detailed-mode.md)；不将地面落点统一视为失败。

## 2.3 已选基底的小范围微调

用户已选定后继阵、只允许小幅位置或角度调整时，沿用以下流程。**默认完整2000起步和迭代，冻结决赛名单后以完整10433收尾；不先跑200筛选，也不强制每个微调新码补200。** 原基底已有三池研究核验复用、只补缺项；用户明确另定阶段时按其范围。评分与池角色以[阵集政策](10-benchmark-usage.md#训练竞争验证与决赛)为准。微调仍需完整阶段证据；改动小不代表胜负变化必然小。

1. **冻结基底与本轮范围。** 从用户明确选择或STATE取纯码，核对原始证据身份并复用已完整核验的基线，只补缺项。分别记录迭代必测池、最终决赛池和用户限定的交付阶段；完整微调也包含冻结决赛圈后的10433，具体政策见[阶段选择](10-benchmark-usage.md#训练竞争验证与决赛)。用户明确仅交付某一阶段时按其范围完成，未测池标未测，不继承父阵成绩。明确总体主目标、关键子群、门槛、同分次序和唯一新码上限。
2. **把“小幅”变成可验收字段。** 列允许slot/字段、方向、角度圆周差及绝对参考阵。位移明确按每组独立还是全阵合计，使用逐轴界限还是欧氏距离；一个联动组内部多个实体同步位移，不自动将其位移重复相加。父阵可以更新，边界仍锚定原参考阵，避免逐代累计越界。角度另设自己的界限。
3. **先画支撑与职责依赖。** 确认移动墙体是否同时要求所撑单位移动才能保持静态零位移。把全部联动字段写入候选与规则，检查诱导目标、治疗覆盖、出手位置和顺序等辅助职责。联动模块的成绩只能归于完整改动；无法通过零位移门禁的“只移其中一件”不能当合法反事实。机制与版本边界查单位百科及[重力审核](gravity-audit.md)。
4. **生成、排旧、审核。** 写短JSON计划，由现有生成器保序生成；按完整纯码在声明的历史范围、批内和跨批去重，保留别名与真实父阵。用户要求旧码不再测时，明确是排除任一阶段已测码，还是仅跳过当前池的完整证据。稳定化后再去重、验规则；所有新码先过静态零位移，再评测。相同成绩不合并不同纯码，审核失败不耗用正式评测冒险验证。
5. **从分离对照转入小联合。** 首批覆盖单项、温和变化和必要反向对照；有效参数再检查条件联合，保留合法F/A/B/AB。默认每个新码直接完成2000，逐池verify且E=0，不套用常规造阵的完整200前置；用户明确指定其他阶段时从其约定。按2.2在本轮迭代池先比较真实父阵及原基底的增/失/净分、关键群N与前后成绩，再冻结下一批；略低总分但有独特子群收益的分支继续保留。
6. **用少量共同对手核验解释。** 从改善与退步各选有问题的对手，复用已有基础/详细证据，确认输入及胜负/HP/结束帧一致。支撑、保护链和火力存活按相关窗口比较；初伤相同仍可能在后续循环分化，不能只凭初伤或整局总次数推断原因。记录支持、否定与不确定，具体反例留本地LEARNING。
7. **在最终几何下复查耦合角度。** 木壁、防区或平台变化后，原角度的单项成绩不能直接迁移。固定每条有力几何分支，对互相保护的单位做用户允许的小范围联合；需要保持角差时联合验收。仅在有收益且额度允许时少量补邻点，不机械铺满大网格。新点胜出后说明是否继续查过下一圈；无新合法点记录零新增，不重跑凑额度。
8. **冻结决赛圈，补完整10433。** 结合迭代必测池、关键群及改动范围确定名单，保留总体有力点、非支配取舍、温和少改和独特对手收益分支；名单与决胜规则在查看新增大池成绩前冻结。全部入围版补齐完整10433、逐池verify，原基底同配置大池可核验复用，跨池重合只补缺局。完整输入不截取，另从结果聚合10235。即使只微移，也不能把迭代池排名直接当最终排名；新增决赛输出与原阶段归档分开，不回写旧manifest。
9. **按取舍交付并收尾。** 并列迭代池与10433/10235的总体、关键子群原始计数、纯胜率/半分得分率、实际新增局数、精确改动和未测范围。若几个版本互不支配，说明多赢哪些群、少多少总分；大池总体冠军与目标群较强版本分别解释，不事后混合大小池权重，也不给次级排序包装成全面更强。按[归档契约](05-experiment-contract.md#实验完成后的本地归档与知识提交)先保存并核验本地结果，再将通用方法合并共享文档并本地提交；具体阵码、成绩和证据路径留本地。

候选生成、先审后评、核验和后台命令沿用本页前文，不另建“微调专用”评测身份。额度是上限；停止扩圈时记录已测邻域和未覆盖联合，不以用满额度或一轮无提升声明全局收敛。

## 交付与知识归档

按阶段报告实际完整的名单与阵池、精确码和改动、原始计数、收益/退步、证据哈希和限制；原游戏未验如实标待验，无提升保留基线。未完成或停止时只保存现场，不标实验完成。完整实验按[本地归档与知识提交](05-experiment-contract.md#实验完成后的本地归档与知识提交)先在本地归档结果并核验，再复核通用知识，仅提交公开文档或工具改动；不推送实验结果。

通用机制进入基础机制/对应百科，方法进入搜索经验/知识专题；具体坐标、角度、用户选择与成绩留案例和实验。共享文档修改前重新读最新内容，保留其他任务新增信息。涉及AGENTS时最后修改。
