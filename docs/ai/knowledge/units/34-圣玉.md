# 圣玉（ID 34）

消耗己方最近死亡兵玉类型，在圣玉附近重建单位。

## 身份与适用范围

| 项目 | 固定值 |
|---|---|
| 编码ID / Rust类型 | 34 / `BallKind::Holy` |
| 军资（工作台目录） | 200 |
| 战斗构造HP | 10 |
| 初始化speed | 300 |

依据Rust提交`149e365221b09330a72d9a6a1804605e3ce4e1f5`与当前`catalog-hp-v1`规则，版本选择见[规则版本](../../unit-hp-rules.md)。本文机制是源码结论；用途与微调建议是基于机制的待测方向，不代表单独胜率证明。军资/中文名来自工作台目录，HP与时序以Rust构造和分支为准。先读[共通规则](common.md)中的兵玉部分；[文档清单](coverage.json)保存单位条目与源码身份。

## 触发与节拍

初始化模300；cnt>305、dead_last非0且不处于jump时触发，cnt归零并清空dead_last。

speed>0时，普通工作台x的初始cnt为`-((x+16)%speed)`；这里的计时是有效递增次数，跳跃会暂停递增，受伤等可能改变状态。speed=0不套取模公式。

## 详细机制与生成对象

- 普通兵玉死亡路径会写dead_last；它是单个最近类型记录，不是死亡队列，也不保存原坐标、原角度或原HP。地面被敌墙碰到的死亡也写入；跳跃越界清理没有该写入。
- HolyGhost沿圣玉朝向偏移38生成，保存圣玉的rot、side、on_side与jump状态；若生成时在车上，它随对应车体移动。
- 幽灵第20次自身更新调用unit_make重建该类型，用新单位构造HP和计时；只额外恢复on_side，第30次清理幽灵。不是在原尸体处续接旧状态。
- 多圣共享同一dead_last，先触发者消耗记录；后续别的死亡可能覆盖想复活的贽玉。

## 受击、恢复与死亡

每次hurt都将cnt归零；死亡按普通兵玉处理。已生成幽灵没有继续依赖圣玉存活的检查。

本体受击、支撑、跳跃、heal与死亡顺序见[共通规则](common.md)。独立生成物不自动随本体死亡消失；依附物是否清理由各自分支决定。

## 改阵与对手诊断

保护圣玉避免反复受击重置，检查死亡顺序、复活出口是否被支撑/攻击覆盖，以及复活后的单位职责。圣贽配合必须核对整条死亡与重建链。

发现对方带此单位时，同样检查它的支撑、保护、实际出手位置与生成对象；先选少量目标对局确认机制是否生效，再用完整评测判断改阵收益。
