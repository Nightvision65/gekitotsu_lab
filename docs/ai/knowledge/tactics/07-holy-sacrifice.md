# 圣贽：思路、攻防与内部变化

用贽玉承担车体或边界碰撞的牺牲，再由圣玉重建贽玉。贽既保护核心免受该次碰撞扣血，也阻止碰撞受击标志触发驻车兵玉受伤；壁玉因此不会仅因这次碰撞而关壁、重置计数。圣贽把碰撞净交换与防区连续性连在一起，不能只理解成核心减伤或复活续命。

机制以[当前后端规则](../../unit-hp-rules.md)和单位源码为依据；用途与改进方向是待检验假设，强度需针对自己的候选评测。

## 如何形成攻击

对方仍承受碰撞而本侧有贽保护时，可以通过多次交换取得优势。防守并非只拖延伤核：免碰撞受伤让已展开的护壁能跨过碰撞时刻继续工作，减少对方趁撞后防区关闭攻入的机会；己方则靠推进和反复碰撞消耗敌核。因此，多壁加速型可以将大量军资投入防护与推进，常规攻击兵很少，甚至不携带常规攻击兵。带近战、核、魔或炮弩的版本另有直接攻击路线，不能把所有圣贽归成相同输出构成。

贽的自我牺牲会在自身HP账本中计为30有效失血，某些归因输出统计也会记到自身，不能把这30算成打向敌方的伤害。

## 贽如何让壁玉在碰撞时保持开壁

源码规则的传递链是：

1. 两车接触时，`GameTask::base_move`先调用`nie_ball_alarm`；找到贽就跳过该侧碰撞扣核心HP及`dokkan_flg`设置。撞边时`Base::step`采用同样的贽检查，跳过该次边界扣血及碰撞受击标志。
2. `Ball::step`对车体上落稳的兵玉检查`jump_flg == 0 && dokkan_flg[on_side]`。该标志未因本次碰撞置位，兵玉便不会仅因本次碰撞而扣1HP、调用`hurt`。
3. 壁玉的`hurt`会令`shooting=false`并重置`cnt`。有贽挡住碰撞受伤时，这条碰撞关壁路径没有触发，现有护壁得以按自己的生命周期继续工作；圣玉也避免了同一碰撞造成的蓄力归零。

因此，“不收壁”准确指**不因受贽保护的碰撞而被迫收壁**。贽不阻止车体反弹、抬升，也不保证护壁永久展开：自然周期收壁、跳跃、直接攻击造成的受伤及死亡仍会使护壁关闭。复活空窗中若没有贽，碰撞仍可伤到兵玉并使壁玉关壁。

源码依据：[mod.rs](../../../../rust/vendor/gkt-core/src/engine/mod.rs)的`base_move/nie_ball_alarm`、[base.rs](../../../../rust/vendor/gkt-core/src/engine/base.rs)的`Base::step`、[ball.rs](../../../../rust/vendor/gkt-core/src/engine/ball.rs)的`Ball::step/hurt`。壁玉自然周期与受伤恢复另见[壁玉机制](../units/19-壁玉.md)。这条碰撞保护链不涉及蓝加速器或电梯壁HP，适用于内置JNI与当前`catalog-hp-v1`源码规则；不同规则下的战果仍分开核验。

## 如何保护攻击链与核心

多壁圣贽的布局围绕一条互相维持的链：**壁保护圣及复活出口→圣重建贽→贽挡住碰撞受伤→壁免于碰撞关壁、圣免于碰撞重置→防区与重建继续工作**。不能只逐枚计算壁玉承伤或圣玉存活，还要看撞击后这个防区是否仍在工作。

布置时，圣、初始贽及重建出口分别核对：圣需要安全蓄力，初始贽要撑过首次接敌，新贽则在圣朝向的出口生成，而非返回原贽位置。贽的报警按单位列表查找，不要求它站在碰撞前沿或贴着核心；位置主要服务存活与支撑。核心、实体墙、加速器共同提供遮挡与支撑，壁玉用不同方向和时序组织防区，迎击、剃等再处理各自能处理的来弹或接近路线。多壁数量本身不保证覆盖完整或无空窗。

圣玉受伤会把cnt归零，最近死亡类型只保存一项，其他兵玉死亡可能覆盖贽记录。贽续接失败后，后续碰撞可能同时关壁、重置圣玉，使断链继续恶化；直接火力也可能先伤到壁或圣，反向破坏整条循环。具体站位按真实支撑、护壁方向、复活出口和实际事件判断，不能把一组坐标推广为所有圣贽的固定模板。

## 怕什么，以及如何判断实际败因

核爆、绕后、突入或持续打断圣玉可绕过仅针对碰撞的保护；复活前的空窗、死亡记录覆盖以及出口遭到攻击都可能断链。防护对象活动存在并不证明圣玉每个方向都安全，多壁之间的相位和几何同样重要。





## 后续改阵的可检验方向

追踪每次碰撞的双方HP、贽报警/牺牲、壁玉本体是否受伤及原护壁是否跨过碰撞继续存在、圣玉是否重置、dead_last后续重建类型与下一次复活。区分有贽保护时的防区连续性、无贽空窗中的碰撞关壁，以及直接攻击造成的关壁；只读核心伤害来源会漏掉保壁价值。优先研究保护蓄力与重建出口的布局，或用小量独立火线限制克制阵。复活数量、壁数量和牺牲次数都不能单独替代胜率。

落到具体阵时，先明确“哪个对手的哪条失效链→只改哪些slot/字段→预计改善哪一群→可能损失哪一群”。先写机制预测，再比较父阵与候选的共同对手；若落点、真实挡点、核心来源或时间窗不符合预测，保留反例并修正解释。不同原阵间的高分差、组件频次与单位目录价格不能替代这个对照。
